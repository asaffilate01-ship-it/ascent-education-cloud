# Centre security, Hikvision integration and facilities — reviewed release

## Hardware architecture
Hikvision cameras/NVR and access readers stay on a restricted on-site network. Use the institution's approved HikCentral Professional OpenAPI gateway (or model-specific ISAPI gateway where supported), not direct browser access to camera IPs, RTSP credentials or internet-exposed device ports. The existing cctv-access function uses a short-lived HTTPS media gateway: configure CCTV_GATEWAY_PROVIDER as hikvision_hikcentral or hikvision_isapi_gateway only after testing the actual adapter, CCTV_GATEWAY_URL, CCTV_GATEWAY_TOKEN and CCTV_MEDIA_HOSTS via server secrets. The gateway contract accepts the selected centre, opaque camera mapping, live/playback mode and time range, viewer identity and provider type; it returns HTTPS media URL, MIME type and expiry (max 15 minutes). The app validates the returned host and audit write before releasing a viewing session. This release does NOT implement or certify the on-site HikCentral/ISAPI adapter, camera health, recording retention, device events, reader programming or fire-panel integration. No network commands to unlock doors, disable alarms or modify emergency release.

Official vendor integration references: https://tpp.hikvision.com/tpp/OpenCapabilities and https://tpp.hikvision.com/products/HCP-Integration and https://tpp.hikvision.com/download/ . Confirm exact device models, firmware, supported API and licensed gateway with the installer.

## Dashboard permissions and records
Verified security officers and centre directors stay within their assigned active centre. A global superadmin must explicitly choose an active centre, with a real null-tenant superadmin role; ordinary staff cannot substitute another centre. Owner access is never an all-centre camera stream. Camera visibility is enabled per camera and security live/playback rights. Direct metadata and permission writes are limited to assigned centre directors, provider IDs and raw credentials never appear in the viewing inventory. Selected-centre owners can view CCTV, physical operations and facilities. Students and lecturers have no security dashboard access. Facilities is a dedicated workspace for those authorised roles, not a new unverified account role.
- Visitor/guest reception: typed acknowledgement by the visitor, host reference, witnessed ID check, policy version and timestamp; one atomic pass, entry event and occupancy update. Checkout is witnessed by the officer and logged; no government ID number or biometric signature stored. Retain and review the actual approved privacy notice and acknowledgement text.
- Local student/staff card register: manager records an opaque approved controller reference, expiry and reviewed issue note; only the hash is stored and never returned to clients. Officer logs an identity-checked observed crossing; matched eligibility, unmatched or denied status and occupancy are recorded. No decision from this application operates a door. On local revocation separately revoke at controller. Access control reader/gateway provisioning and automatic controller events are future integration, and independent offline operation/emergency egress must be preserved.
- Facilities: record actual surveyed entrances, emergency exits, fire extinguishers, manual alarm points, fire panels, assembly points, emergency lighting, fire doors and first aid. Map is an optional coordinate index relative to a named surveyed plan revision; it is NOT a building drawing, fire-engine access route or approved evacuation plan. Do not invent locations or determine extinguisher type/number/placement by generic rules. Obtain the real Jhelum plan and local competent fire safety assessment, including applicable Punjab Emergency Service/Rescue 1122 requirements, physical posted plans, accessible escape routes, alarm tests, extinguishers, drills, inspections and maintenance. Dashboard observations do not certify compliance. Site checks are append-only; review history and local card changes and signed acknowledgements are accessible as bounded recent audit datasets.
- CCTV audit lists recent allowed viewing-session requests; security officers see own viewing audit, managers see selected-centre records. No export/re-identification/face recognition. No cameras in toilets, changing or private welfare spaces; disable audio by default and document purpose, privacy notices, retention, authorised disclosure, safeguarding and staff training.

## Installation
Read-only production inspection confirmed unipathway_cctv_cameras and cctv_access_events exist while the legacy centre credential, visitor, access, occupancy, zones, devices and muster tables are absent. Confirm the whole preflight inventory again before installation. Generate reviewed SQL only:
`node scripts/activation/build-unipathway-site-operations.mjs --print-sql`
It extracts only table definitions from the three original physical security migration sources, rejects existing/partial physical schemas, enables RLS and revokes raw client grants, installs existing scoped physical operations plus the new forward candidate in one transaction. It does not run hosted SQL, modify migration history, configure hardware or certify a building. It revokes legacy unsigned visitor entry and narrows direct CCTV metadata grants; coordinate frontend and server deployment before use. Keep both base physical flags and site writes off until independent backup/restore, operator authorization, actual two-centre JWT and real provider acceptance. Frontend requires VITE_UNIPATHWAY_PHYSICAL_SECURITY_ENABLED, VITE_UNIPATHWAY_PHYSICAL_VISITOR_WRITES_ENABLED, and VITE_UNIPATHWAY_SITE_OPERATIONS_ENABLED as appropriate. No real emergency response or live CCTV availability claimed from synthetic tests. The standalone facilities-manager role, actual approved floor-plan image overlay, automated provider card events, physical access programming, muster writes, and full retained audit export remain separate follow-up work.
