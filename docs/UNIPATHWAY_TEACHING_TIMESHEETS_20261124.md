# Teaching timesheet workflow — controlled release

The part-time teaching workflow adds persistent dated claims rather than using scheduled hours as payable hours. A verified lecturer chooses a past/completed occurrence of their currently assigned active weekly class (PKT), enters whole minutes up to the planned duration and an evidence reference. The server verifies current role, module, tenant, weekday, effective dates, time elapsed, schedule revision and overlaps. Duplicate exact submissions return the existing receipt; a different claim for the same scheduled occurrence is rejected.

A verified centre director can independently approve or reject a claim with a review note; self-review is prohibited even for a multi-role user. Decisions are final within this version, and corrections, overtime, cancellations and historical reassignment require a separate authorised exception workflow. The finance role receives only approved rows and aggregated approved minutes/sessions, not evidence references or private review notes. No contracts, rates, payment batches, payroll authorisations, deductions or bank transfers are created.

`scripts/activation/unipathway-teaching-timesheets-forward.sql` is an intentionally one-time reviewed forward candidate, not part of automatic migration replay. It creates private RLS-enabled tables without direct client access, narrow role-checked RPCs, and disabled read/write gates. Confirm the actual project, source tables and types, backup and recovery, schema inventory, security review, authenticated role/JWT tests and timetable acceptance before applying. Enable reads first and writes only after acceptance. The front end independently requires `VITE_UNIPATHWAY_TEACHING_TIMESHEETS_ENABLED=true`. The release must not be represented as live from GitHub CI alone.

The dashboard panels use responsive forms, role-scoped receipts, verified read responses, bounded result sets, pagination, explicit errors and exact retry semantics. CI runs a synthetic two-centre database rehearsal and frontend response validation. Real production identities, schedules, attendance evidence and payroll must not be seeded with synthetic records.
