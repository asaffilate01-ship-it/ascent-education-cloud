# UniPathway — All-role dashboard functionality, process handoffs and permissions
**Source audit and implementation specification: 1 November 2026**  
Repository: `asaffilate01-ship-it/ascent-education-cloud`, development PR #177.  
**Audience:** platform owner, centre director, academic/office/finance staff, students, agents, guardians and approved external partners.  
**Sign-in portal:** https://unipathway.pk/login.

## Status definitions and boundaries

- **Source-wired** = current React routes invoke named Supabase tables, Postgres RPCs or Edge functions. This is not proof of a functioning hosted service.
- **Staged/off** = the code, forward-patch SQL or gateway exists but is gated pending trusted backend deployment, secrets and authenticated two-centre acceptance.
- **Not connected** = no verified end-to-end implementation or verified external provider. Do not advertise as operational, show invented metrics or activate buttons that cannot finish a transaction.
- Access to `user_roles`, `profiles`, applications, student/enrolment/medical/financial records, private files and provider accounts is denied by default unless a current role, centre and record-specific server policy permits it.
- The linked Supabase connector currently lists **DISHBEE only**, not UniPathway. Never apply these patches to that unrelated project. Current findings are GitHub source and synthetic test evidence.

## B. Mandatory handoffs / state machines

1. **Recruitment** — Marketing tracks anonymised source → Agent (only if assigned) contributes verified referral → Admissions registers application → permissions/comms apply to applicant records. No agent/marketing route can grant academic eligibility.
2. **Admissions and academic provisioning** — verified contact + KYC/qualifications + programme eligibility + funding/offer → signed enrolment action → learner account/active programme → course module permissions and timetable. Any failed step must be recoverable and auditable; never imply a deposit was received from a kanban move.
3. **Teaching** — Programme Leader assigns lecturer to approved module → timetable and class invitation → learner-specific attendance / class participation → coursework brief and submissions. Teams and lab launch require independent provider configuration and applicable budget/consent.
4. **Assessment** — assessment submitted → allocated independent Assessor → rubric-based human mark with revision → independently allocated IQA approve/return → separate release → Student results → optionally Guardian results after learner consent → independently approved EQA evidence sample. Prevent double roles, unassigned reads and stale edits.
5. **Examinations and qualification** — Exam Office verifies official entry + identity, venue, invigilators, assessment integrity and board result → authorised import/QA → official result record and appropriate certificate process. Do not equate internal coursework results with a regulated board result.
6. **Finance** — authorised invoice + agreed student/sponsor shares → provider-signed payment or supervised manual verification → bank/ledger reconciliation → invoice adjustment/refund → audited reporting → agent/university commission only under separate contract and verified source records. No fictional revenue or multi-currency aggregation.
7. **Progression and employment** — approved student profile/CV + chosen overseas university or employment opportunity + explicit disclosure consent → institution/employer receives only the relevant application → independent offer/interview/placement decision → learner tracks progress. No automatic visa, employment or university acceptance guarantee.
8. **Centre operations and safeguarding** — Centre Director delegates personal office capabilities → office/admin tasks and approvals → learner and staff support, authorised welfare case management and CCTV incidents. Role switching must not retain old privileged screens or cached data.

## C. Permission-check contract: every protected action

- Authenticate a fresh current session, then validate currently assigned `user_roles.tenant_id` against `profiles.tenant_id`, chosen active role and centre.
- Authorise the specific operation and record: tenant, student/guardian link, agent ownership, employer organisation, lecturer allocation, assessor/IQA assignment, proof of consent, validity period and resource/provider scope as appropriate.
- Check on **server RLS or a tightly grant-controlled RPC/Edge function**; never accept checkbox, client route/tenant ID, free-text role or `user_metadata` as permission.
- For create/update/approve: validate actor, incoming fields, current workflow state, idempotency, revision, audit, and rollback on failure. Return verified created ID/state, not just an optimistic toast.
- For sensitive documents, results, medical and CCTV: minimise selected fields and row counts, expiry for signed URLs, download audit, no cross-centre cache reuse, and revoke access immediately when an assignment or sharing approval ends.
- For disabled providers, use a clearly labelled unavailable state and link to the appropriate authorised owner. No placeholder accounts, fabricated outcomes or automatically started paid resources.
