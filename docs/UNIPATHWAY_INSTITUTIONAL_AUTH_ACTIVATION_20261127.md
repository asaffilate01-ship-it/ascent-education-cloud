# Institutional account security — 27 November 2026

Do not activate on the wrong Supabase project. The currently connected project inventory does not contain UniPathway. This release prepares a closed institutional login flow; it does not change live Auth settings, approve existing users or certify every privileged endpoint.

## Account onboarding and recovery

- Disable public signup, anonymous users, OAuth/social providers, public self-assignment and identity linking in the actual Auth project. Set the Site URL to https://unipathway.pk and restrict redirect URLs to approved HTTPS and verified native callbacks. Require email confirmation and a minimum 12-character password, breached-password checks where available, and appropriate Auth rate limits.
- Provision the institutional mailbox first. Administrators create the Auth user and centre profile, assign only the approved role(s), and record the immutable Auth user ID and exact lowercase address in unipathway_identity.approved_accounts with an approval reference. Do not bulk-approve existing domain accounts. Verify all staff, students and global administrators individually; reconcile legacy logins and protect a separately verified break-glass administrator. The existing staff-invitation workflow assigns roles, but does not automatically insert into the new approval registry. Complete approval before the invite is used.
- Prefer a one-time invitation or password-setting link over emailing an initial plaintext password. If a temporary password is used, it must be individually generated and handled through an approved secure onboarding procedure, with a verified forced-change mechanism before access; this release does not implement a server-enforced temporary-password change marker. Never retain or send passwords in email, logs or Git.
- Require the built-in TOTP authenticator on every account. AAL1 can access the Auth service for approved factor enrolment, verification and recovery, but not protected application data after the reviewed RLS overlay. Email confirmation/OTP and Resend recovery are not an alternative AAL2 factor. Lost authenticator recovery must be administrator-reviewed with identity checks, revocation of old sessions and controlled factor reset; never silently downgrade MFA.

## Hosted enforcement (review required)

1. Identify the actual UniPathway project and verify the deployed schema, backup/restore and auth.users/auth.sessions columns. Rehearse scripts/activation/unipathway-institutional-auth-forward.sql and scripts/activation/unipathway-institutional-rls-forward.sql in an isolated database. The latter is a restrictive policy overlay for existing RLS-enabled public/storage tables, not a replacement for centre-specific permissions; it refuses exposed authenticated tables without RLS. Inventory additional schemas, views, column grants, realtime, storage signing, security-definer functions, scheduled jobs and every service-role/edge endpoint, including old self-provisioning RPCs. Disable or guard every bypass before activation; direct authenticated SECURITY DEFINER functions are not automatically protected by table RLS.
2. Populate the private approval registry, including recovery accounts, then configure Custom Access Token Hook to the reviewed PostgreSQL function (unipathway_identity.institutional_token_hook). Validate actual hosted auth hook privileges and schema support before registering it. Test external emails, unapproved domain accounts, suspended centres, wrong memberships, revoked sessions, changed email and AAL1/AAL2. Auth token issuance and data access are different: approved AAL1 is needed for setup, while protected access requires native AAL2 and the current session row.
3. Disable or protect old registration and automatic account bootstrap functions. Reconcile the initial invitation flow with the approved-account registry and exercise invite/recovery with real mailboxes. Verify the dashboard role-switch and direct REST/RPC/storage paths with both approved and denied users. No legacy permission may override the restrictive policy. Existing signed URLs and access tokens must be considered in revocation tests.
4. Only once all checks pass, coordinate VITE_UNIPATHWAY_INSTITUTIONAL_AUTH_ENABLED=true (browser build) and UNIPATHWAY_INSTITUTIONAL_AUTH_ENABLED=true (shared authenticated edge handlers). Test native clients too. Retain a controlled rollback and revoke stale sessions. The shared auth helper's check does not cover functions that implement their own authentication; explicitly inventory and guard them before launch.
5. Keep application access fail-closed and record evidence. Future tables and RPCs must receive equivalent policies. No arbitrary client-supplied role, email, IP or user ID establishes access.

## Login IP and privacy

The private current_login_sessions view reads Auth-recorded session IP, user agent, creation/update times and assurance level. It is not exposed to browser roles and does not retain historical sessions after deletion. Enable Supabase Auth audit log database storage and appropriate log retention. Verify actual IP availability, link relevant security events to sessions and design an append-only, role-scoped historical audit register before claiming complete login history. IP-derived geography is approximate and may reflect VPNs, mobile networks or proxies; do not collect device GPS or expose IP history to unrelated staff. Document retention, access, incident review and privacy notice.

## Resend Auth email settings

In the actual UniPathway Supabase Authentication SMTP settings, use smtp.resend.com, port 465 (SSL), username resend, password the existing restricted sending API key, sender name UniPathway, sender email accounts@unipathway.pk. Confirm the domain is verified in Resend, including SPF/DKIM and appropriate DMARC. Disable click/open tracking for authentication messages. Configure Auth templates using the HTML files in supabase/templates/unipathway; use the provider's single-use ConfirmationURL or Token per verified flow. Enable password-changed, email-changed and MFA factor security notifications. Sending domain verification is not an inbox: provision real receiving mailboxes for every issued account, admissions and jobs via the chosen mail hosting provider. Do not overwrite receiving MX records merely to send mail.

No real API keys or secrets are in this repository. Configure the Resend credential in the actual Auth settings and the application's server-only edge secret store; never VITE_ variables or public code.
